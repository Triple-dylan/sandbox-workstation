October 28, 2026. This records the research/interview process that preceded the rebuild plan. **The user subsequently approved `Rebuild Plan.md`; stage A is authorized, with a design-review gate before broader implementation.** The statements below about the earlier interview/implementation pause are historical. Findings remain distinct from selected production services or accepted visuals. The existing prototype remains rejected.

**Latest review:** `Maturity Refinement Plan.md` adds the 8:58–8:59 PM screenshot/source audit, refreshed research and a second reflection on composer/actions, mature conversations and agent build/deployment. The user now specifically requires monochrome graph/rail/icons/right modules and removal of the center glyph. That supersedes blue control accents and the earlier monochrome-superseded wording below. ## Latest confirmed direction

The user chose desktop-style snap regions with placement feedback and neighboring modules resizing. Working modules must never overlap; the workspace is bounded rather than an infinite pan/zoom surface. No application-level zoom controls belong in the composer. The graph has an anchored central node with limited displacement and a restoring force; other nodes have more movement. Physics stays enabled.

Conversation navigation can extend from the left rail. A selected DM should replace the active conversation while preserving the open document; quick reply is a possible supplement still to evaluate. Right-side utilities are sources/context, agent controls and goals, with several visible concurrently. Conversations do not belong there. The combined Goals/Knowledge/People/Agents Project module is rejected.

A selected graph document/folder should open a document viewer or node explorer as a module. The Codex screenshot specifies the quality/style of a module, not a mandate to copy every behavior of its popover. Precise expanded-view behavior still needs resolution against the no-overlap rule.

The user also rejected the muted gray design and requested a new UI/design system with more Liquid Glass. Earlier monochrome, nearly square-card and free-canvas recommendations are superseded. Earlier business, privacy, canonical-sharing and automatic-context requirements remain in force.

## End-to-end situations the later plan must account for

- **Start privately:** new conversation opens without naming paperwork or a required project; human/agent recipient intent is clear; unsent text and attachments retain their audience when navigating.
- **Enter a shared project:** conversations/channels are navigable from the left; sources, goals and agent modules coexist on the right; personal arrangement does not alter shared content.
- **Open work:** a document, spreadsheet, browser or graph explorer receives a valid snap region. An already open resource can be focused. When space is exhausted, the outcome is explicit rather than overlap, shrinking below readability or losing a module offscreen.
- **Use knowledge:** folders expand intentionally; selecting a resource opens a viewer/explorer module with access checks. Return restores the graph branch and centered orientation. Node appearance, labels and actions must be understandable in realistic data, not only a tiny sample.
- **Collaborate:** simultaneous edits converge; presence expires; reconnect restores real work; shared resource state and personal navigation remain separate. An offline/pending update cannot pretend to be saved remotely.
- **Ask an agent:** personal autonomy settings and collaborative approval rules govern execution. Routine context maintenance remains automatic. Approvals show actual proposed changes and stale proposals are revalidated.
- **Share:** change the canonical original's scope explicitly, preserve attribution/revisions and avoid leaking its private source conversation. Only an explicit variant creates a new identity. Referenced attachments also need valid access.
- **Use integrations:** file changes and browser/connector results enter the same resource/context/history model. Connector credentials belong to the appropriate user/service account; project membership alone does not disclose a personal session.
- **Leave and recover:** module visibility, job lifecycle, durable data and notifications are separate. Retirement behavior remains unresolved; closing a UI surface must not accidentally impersonate cancellation or deletion. Error and recovery behavior need their own observable states.

## Reflection after the final clarifications

The user confirmed that chat, graph and an open work window must sometimes coexist. The main area must not become a single mutually exclusive chat-or-graph-or-document page. This does not mean every module is preloaded, every document becomes a window, or all modules must remain visible below their readable minimum sizes. One document viewer is retained; browser and agent-editing modules have independent purposes.

The user also accepted private personal connections plus explicitly added shared project connections. Add account ownership and authorization to the product contract; do not silently broadcast a personal browser session or expose connection secrets through project membership.

The reflection found these gaps in the earlier effort:

1. **Coexistence and continuity:** one working arrangement must combine conversation history/input, graph and a resource viewer when needed. Selection, reading location, draft, graph subject and module placement are separate state, not side effects of a global current-page variable.
2. **Graph meaning:** folder containment, an explicit reference, an actual agent access event and an inferred similarity are not interchangeable edges. An attractive graph without an answer to “why are these connected?” would remain superficial. A vector similarity is not evidence of causal dependency.
3. **Actionability:** context needs precise, useful actions tied to canonical resources and revisions. Another layer of folders or decorative graph animation would not solve handoff burden.
4. **Web-first feasibility:** full browsing does not require a desktop-first reversal. A web client can embed a remote browser's interactive display instead of directly framing the destination site. This is a capability to prove, not a selected service or a promise that every site works.
5. **Quality evidence:** actual compound workflows and adverse states must establish quality. Old assertion counts and isolated button tests did not establish non-overlap, comprehension, genuine collaboration or native file behavior.

Keep the conversation's recipient/scope unchanged and reference the canonical item/revision rather than duplicate it. | T3's [typed context records](https://github.com/pingdotgg/t3code/blob/e34067edef2eba03c1e40bca7d2b2d933ae12b85/docs/internals/composer-context-references.md) separate durable payload identity from display references. | **Catch me up** | On request, summarize changed goals, meaningful document changes, decisions, completed agent work and approvals since a personal last-seen point. | **What does this change affect?** | Inspect a changed source and identify generated outputs that used its older revision. **Priority judgment:** precise context selection fits naturally into the initial resource/chat integration. A source-linked catch-up can build on the required event/history/context foundations. Dependency-impact inspection and richer teammate handoff are optional later enhancements. Automatic project orientation, provenance, graph activity, canonical sharing and approvals were already requested; do not rebrand them as new optional innovations.

## Additional feasibility evidence for a web-first browser

[Browserless Live URL embedding](https://docs.browserless.io/baas/monitor-sessions/embedding-live-url) documents embedding an interactive remote browser display, with server-controlled view-only/input modes and sizing. Its [session documentation](https://docs.browserless.io/overview/getting-started/create-a-browser-session) distinguishes browser reconnection from viewer-link lifetime. This is different from placing an arbitrary destination URL in an iframe. Service access, session isolation, latency, reconnect, login and rendering need actual proof before selecting a provider. No account was created, credentials supplied, remote browser started or paid service selected during this research.

A [T3 portable handoff](https://github.com/pingdotgg/t3code/blob/e34067edef2eba03c1e40bca7d2b2d933ae12b85/docs/user/portable-handoffs.md) also distinguishes saved conversation context from provider-specific internal state. Our orientation/handoff design must retain retrievable original history and source references, rather than assume an agent summary transfers an entire running agent's state.

Quick reply is a useful optional supplement to ordinary conversation navigation. [VS Code Quick Chat](https://code.visualstudio.com/docs/chat/inline-chat) demonstrates a temporary interaction that can continue in the full conversation. For human DMs here, the proposed adaptation is an inline, space-allocated reply in the extended conversation rail, retaining the existing DM and leaving the main composer/draft untouched. It should not become another overlapping chat window or a second hidden conversation.
